# Fortleva Work Management — adversarial reviews of the three plan drafts (2026-08-16)

*Two independent reviewers (constraint-fit; requirements-coverage + autonomous buildability) of the architecture / UX-product / sequencing drafts. Every issue below was resolved into one pinned decision in the approved plan; kept here as the rationale record.*

## Review — verdict

The three drafts converge on the right product (ADO data model, Planner/Linear surface, first-class time, portal-as-projection, server-side vault) and every element of the founder's request is concretely covered somewhere. But they disagree on ~8 load-bearing points (phase order, where Notification/outbox/ProjectUpdate/portal-comments land, issue:* retirement, cost-rate storage, ProjectTimeSummary shape, SavedView, depth wording, route names) and Claude Code cannot build from three plans. Merge into ONE sequence: P1.5 (i18n, UI kit, R2 transport, request-context, MFA step-up, v2 AAD crypto format, app.principal_id GUC) → P2-minimal (Client, Project+key/portalEnabled, MemberClient/MemberProject, scoping union, Document attach; defer Milestone/ProjectVersion/Service/export to P3) → W1 Work (items/states/rank/board/backlog/My Work/Comment/Activity/search_index; notify.emit() signature + in-app Notification table stub) → W2 Time (TimeEntry/RateCard/Budget/rollups/money page/StaffNotice) → P3 Portal (Contact identity, sharing UI, ProjectUpdate + timeline, portal REQUEST intake, client comments, hours widget computed on read) → V Vault/Assets → P5 Collaboration (outbox/SES/digests/inbox/triage polish) → P4 Money (+time→invoice bridge) → P6 Reports → P7/P8. That gets Naxdor onto boards by ~week 8-9 and timers by ~week 12, keeps every one-way door in the first migration that needs it, and matches the ux draft's D1 (collab before money). Fix the blockers below before handing the merged plan to Claude Code.

### Strengths
- All founder asks map to concrete tables/screens/tests: kanban+backlog (WorkItem/WorkflowState/rank), ADO-like hierarchy (Epic>Task>Subtask), per-task timer (TimeEntry stoppedAt NULL + partial unique), rollups per member/team/project/client, project hourly rate + cost/margin (RateCard BILL/COST tiers, snapshot on entry), selective client visibility (existing Visibility + RESTRICTIVE portal_gate, verified present in 20260808191500 migration), progress reports with timeline (ProjectUpdate + derived Client Timeline), assets (Document reuse), credentials per client/project (CredentialItem + envelope crypto).
- One-way doors are correctly identified and pulled forward (rank COLLATE C, number via TenantCounter, kind/TRIAGE enums, child<=parent visibility CHECK, TimeEntry constraints, v2 AAD ciphertext, app.principal_id GUC, search_index TS config) — this is what makes later phases additive.
- Every phase lists models, permission codes with role seeding, audit events, module key, screens, the four test families and a demo script — the right granularity for autonomous build; the sequencing draft's fallbacks (local StorageTransport, dev outbox, lazy timer effects on Hobby) remove founder-credential blockers.
- Honest pushback is present and correct: ADO clone is the wrong target; tidsredovisning-not-övervakning never-list; vault liability stated; Vercel Pro dependency named; RLS/GIN performance edge documented; stale docs (PLAN skip-list l.310 verified, DATA_MODEL §11, AUTHZ catalog test = 63 verified) enumerated for dated decision entries.
- Explicit what-NOT-to-build lists in all three drafts keep the solo build inside a fixed screen set.

### Issues

**[blocker] Merged sequence / conflicting plans**  
Three drafts give three phase orders and three homes for the same tables: Notification+EmailOutbox in 2W (architecture) vs P5 (ux) vs stub-in-W2 (sequencing); ProjectUpdate in 2T (architecture) vs P3 (ux, sequencing); client comments in P5 (ux — meaning the P3 portal ships with no way for a client to reply) vs P3 (sequencing); P4 before P5 (architecture, sequencing) vs P5 before P4 (ux). Claude Code cannot execute from this; the founder will be asked to arbitrate mid-build.  
*Fix:* Adopt one order: P1.5 → P2-minimal → W1 → W2 → P3 (with ProjectUpdate, portal REQUEST intake, client comments, hours widget) → V → P5 → P4 → P6 → P7/P8. Land notify.emit() signature + Notification/Subscription tables + kind catalog with audience flag in W1 (in-app only), EmailOutbox/SES/digests in P5. Write it once into PLAN.md §3 and delete the alternatives.

**[blocker] Portal RLS + Project.portalEnabled**  
All drafts require the RESTRICTIVE portal policy on WorkItem/Comment/ProjectUpdate/search_index to honour Project.portalEnabled, but only the sequencing draft says how (denormalise portalEnabled onto each row via trigger); the architecture draft says 'or denormalised flag' and leaves it open. The existing portal_gate on document (verified) is a pure column comparison; a subquery to project inside a FORCE-RLS policy re-evaluates project's own policies per row and, for a contact principal, project must itself be CLIENT_VISIBLE — an easy way to get a fail-open or a silent empty portal. This is the exact bug class the product calls the worst.  
*Fix:* Decide now, before W1's first migration: denormalise `portal_enabled boolean` onto every class-B work table (trigger on project UPDATE fans out inside the same tx), policy = `client_id = app.client_id AND visibility='CLIENT_VISIBLE' AND portal_enabled`. Add to the posture test: every clientScoped table has client_id, visibility, portal_enabled and a policy named portal_gate. Test: flipping portalEnabled off yields 0 rows for a contact across all tables.

**[blocker] Autonomous buildability — spec ambiguity Claude will trip on**  
Small but concrete contradictions across drafts that will each cost a session or a migration: hierarchy written as 'depth ≤ 3' (ux, sequencing) vs 'depth ≤ 2 from root / CHECK depth <= 2' (architecture); WorkItem.assigneeContactId column in W1 with a CHECK referencing it (architecture, sequencing) vs added in P3 (ux); home route `/my-work` vs `/home` vs `/work`; StateCategory TRIAGE state auto-created 'hidden' (sequencing) vs created only on triage; permission code names differ (work_item:manage_workflow vs workflow:manage; time:lock vs time:manage_locks; cost_rate:view vs rate:view_cost vs cost:view; module `budgets` split out only in sequencing).  
*Fix:* In the merged plan pin every enum, column, route and permission code once, in a single 'W1 spec' and 'W2 spec' section (depth as 0-indexed with EPIC=0, TASK=1, SUBTASK=2 and CHECK depth <= 2; assigneeContactId in W1; home = /home; codes: workflow:manage, time:manage_locks, rate:view_cost, one module `time` covering rates/budgets). Claude should never have to pick between drafts.

**[major] issue:* codes and AUTHZ immutability**  
ux draft recommends deleting the five issue:* codes and the `issues` module key 'before any tenant data'; verified: AUTHZ.md l.45 says codes are immutable forever, deprecate-and-add, and Naxdor is already provisioned with RolePermission rows for them (catalog.ts l.92-96, TEMPLATE_VERSION 1). Deleting sets a precedent that the immutability rule bends when convenient — the rule exists precisely so future sessions don't argue this.  
*Fix:* Follow architecture/sequencing: keep issue:* in the catalog, mark deprecated in description, drop them from TEMPLATE_VERSION 2 templates, keep `issues` in entitlementsSchema as a deprecated alias of `work`. Record in AUTHZ.md as the first deprecation.

**[major] Cost-rate storage (salary-grade PII)**  
ux draft stores `costRateEnc` on every TimeEntry (fan-out of encrypted salary data across the hottest table, and any reprice must rewrite ciphertext); architecture stores cost only on an immutable RateCard row with the entry holding costRateCardId. The synthesis §7.2 explicitly warns against per-entry cost fan-out.  
*Fix:* Adopt architecture's model: RateCard rows immutable (close+insert), COST amount encrypted once on the card with AAD rate_card:id:amount, TimeEntry.costRateCardId only, aggregation = SUM(seconds) GROUP BY cost_rate_card_id then decrypt a handful of cards behind rate:view_cost + step-up. Bill rate snapshotted as plaintext amount on the entry.

**[major] ProjectTimeSummary over-engineering**  
architecture proposes a physical class-B ProjectTimeSummary table with per-write delta upserts + nightly self-heal + derived visibility that must flip when hoursSharingMode changes; ux says view/read model. For a 1-15 person agency a SUM over (tenantId, projectId, startedAt) is milliseconds; a maintained projection adds a consistency bug surface (and a property test) for no v1 benefit.  
*Fix:* P3: compute hours widget on read via an allow-listed function in modules/time/portal.ts run under system principal with the same forbidden-columns grep (only billableSeconds, budget %, per-month; never memberId/rates). Materialise only when a tenant's query exceeds a measured threshold. Keep the RLS invariant that a contact principal reads 0 time_entry rows.

**[major] Time-to-value / P2 scope**  
All drafts still put 3-5 weeks of Phase 2 (Milestone, ProjectVersion, Service, export v0, /settings/preferences UI, timeline view) before W1, so Naxdor's first daily-use value lands ~week 9-11. W1 needs only Client, Project (+key, portalEnabled), MemberClient/MemberProject, the scoping union and Document attach.  
*Fix:* Split P2 into P2-minimal (2 wk: Client, Project, assignments, authorizedClientIds() union, assertInScope, Document attach UI, Project.key) → W1, and move Milestone/ProjectVersion/Service/export v0 into P3 where the portal first needs them (WorkItem.milestoneId can be added in P3 as an additive column). Saves ~2 weeks on the critical path.

**[major] Under-scoped: 'team' view and project templates**  
Founder asked for 'kanban, backlog, team'. The team surface (group-by-assignee board / People view with counts and hours, member workload at a glance) is tier S and not in any W1 screen list; ProjectTemplate is M in the synthesis but sequencing pushes it to P6 while W1 states presets are 'code-side constants, tenant-editable later'. Templates are how an agency spins up its 20th near-identical web-build project; that is week-one need at Naxdor.  
*Fix:* W1: make group-by-assignee on the board (same <WorkItemView>) and a /projects/[key]/team panel (members on the project, open items, Σ estimate; NO time or presence) part of W1's screen list. W1: tenant-editable WorkflowPreset + ProjectTemplate (states, epics, items, checklists, visibility) with 'save project as template' — cheap once WorkItem exists; W2 adds Σ logged to the team panel.

**[major] Over-scoped for v1 (1-15 person agency)**  
Items marked M/S that a solo founder should not build before a tenant asks: offline timer event queue with skew clamp/reconciliation (M-mobile in synthesis; sequencing/ux keep it in W2 API); SavedView + Favorite tables in W1 (ux, sequencing) while URL state via nuqs already covers views; Reaction and Mention tables in W1; WorkItemLink with acyclic BLOCKS check; WIP limits + definitionOfDone; CredentialShareLink with passcode+email-verification+includeTotpCode and per-item TOTP in V v1; AssetCheck RDAP/TLS; per-project RoundingRule with three modes in W2 before any invoice exists; ProjectUpdate templates + schedule + auto-draft in P3.  
*Fix:* W1: drop SavedView/Favorite/Reaction/WorkItemLink/WIP/definitionOfDone (keep Mention only as extracted ids on Comment for notifications). W2: timer/entries/rates/budget/rollups only; offline queue and RoundingRule move to P4 (rounding is an invoice-line concern). V v1: CredentialItem+Secret+Version, reveal/copy with step-up + audit, ClientAsset + expirations; share links (view-once, TTL) yes, passcode/email-verify/TOTP-in-link and AssetCheck later. P3: ProjectUpdate manual + immutable; schedule/auto-draft/templates in P5.

**[major] Founder vocabulary trap: 'cost per hour for that project'**  
The founder's request ('add cost per hour for that project so it can calculate the cost') almost certainly means the client-facing hourly rate × hours = what the work costs the client. All drafts split this into BILL rates (what you charge) vs COST rates (salary, encrypted, finance-only). If the plan is handed over without mapping the founder's word 'cost' to BILL and stating that internal COST is a separate optional layer, the first W2 demo will surprise him and the money screen will feel wrong.  
*Fix:* Add a decision item at CP2: 'Your "cost per hour for the project" = Fortleva bill rate (project-scope RateCard kind BILL); Fortleva also supports an optional internal cost rate for margin — do you want that in v1 (default: yes, encrypted, CEO-only)?' and label UI accordingly (Rate / Value vs Internal cost / Margin).

**[minor] Hidden blockers for autonomous execution**  
(1) The staff-notice acknowledgment gate means Naxdor cannot use timers until the founder writes/edits sv+en notice text — fine, but the plan must ship a draft text so W2 is demoable. (2) UI kit visual approval (CP1) is a human gate before W1 multiplies components; if the founder is absent, Claude stalls or builds the wrong look. (3) `withRequestContext` exists (src/lib/request-context.ts) but is not wired — all drafts note it; needs to be a P1.5 checkbox with a test that audit rows carry requestId. (4) `authorizedClientIds()` TODO line cited as 99 (ux) and 105 (sequencing) — trivial, but shows drafts weren't cross-checked. (5) btree_gist EXCLUDE and the `fortleva` text-search config with unaccent in a GENERATED STORED column need a Neon verification spike; if unavailable the fallback (app-level overlap check; STORED tsvector without unaccent) must be pre-decided.  
*Fix:* P1.5 gets: draft sv/en staff notice text in the seed; a 'default: shadcn neutral preset, proceed if CP1 unanswered in 48h' rule; withRequestContext wiring + test; a 1-day Neon spike (btree_gist EXCLUDE, CREATE TEXT SEARCH CONFIGURATION, IMMUTABLE f_unaccent) whose result is written into the W1/W2 migrations as a decided fallback.

**[minor] Vault portal path consistency**  
architecture says (time) 'no system-principal bypass in any portal path' but (vault) 'portal reveal goes through reveal.ts under a system principal that re-checks visibility'; TENANCY.md l.236 already permits brokered system-principal writes for contact-caused actions, so the pattern is allowed, but the plan states two opposite rules.  
*Fix:* State one rule in the merged plan: portal reads go through RLS-scoped contact principal; contact-caused writes and secret decrypts are brokered under system principal after authorizePortal(), and every brokered function lives in modules/*/portal.ts and is covered by the forbidden-columns grep and the contact-writable census test.

## Review — verdict

Adopt the ARCHITECTURE draft as the base (it is the only one that keeps every new table inside the existing RLS-class / composite-FK / denormalised-clientId conventions and names the GUC + registry changes needed), take the UX draft's screen/interaction catalogue and the SEQUENCING draft's checkpoints/fallbacks — but do NOT start any migration until the contradictions below are resolved in a single reconciled PLAN.md table. Three items are outright violations of standing rules (portal route holding the BYPASSRLS credential / no-login secret links; the `Project.portalEnabled` gate having no agreed data-layer mechanism; a Sweden-specific text-search config baked into a one-way-door table), and roughly six load-bearing designs differ across drafts (contact-writable census, ProjectTimeSummary shape, cost-rate storage, module keys, notification placement, ProjectUpdate placement). Everything else is additive on seams that already exist (withTenant/withPlatform, requireAccess, record(), TenantCounter, Document/FileObject, TenantPreference, Visibility+portal_gate template).

### Strengths
- All three drafts respect the hard rules the codebase actually enforces today (verified against prisma/schema.prisma, migration 20260808191500 and src/db/model-registry.ts): tenantId-first indexes, `@@unique([tenantId,id])` composite-FK targets, class-A `portal_deny` vs class-B `portal_gate` split, denormalised clientId on every portal-reachable row, DB default `INTERNAL`.
- The architecture draft correctly identifies gaps the code confirms: `authorizedClientIds()` still returns `[]` (src/authz/authorize.ts:99-107), `authorize()` has no `requiresMfa` enforcement, `withTenant()` sets only tenant/principal/client GUCs (no principal id), and `field-encryption.ts` implements no AAD even though SECURITY.md §6 already specifies `tenantId||model||field` — so its Phase-2 one-way-door list (principal_id GUC, v2 AAD format, registry subclasses + posture test) is the right pre-work.
- TimeEntry as class A with a separate portal projection, RateCard immutability with card-id snapshot, cost rates never on entry rows and never in AuditEvent metadata, staff-notice acknowledgment before first timer, and the explicit never-list (idle/screenshot/presence/leaderboards) are all consistent with SECURITY.md's minimisation posture and with the founder's EU/labour-law constraints.
- Merging Issue/IssueComment into WorkItem(kind=REQUEST)/polymorphic Comment keeps DATA_MODEL.md §10's rule (hard clientId+visibility columns for authorization, soft pointer only for anchoring) and reduces the number of comment/attachment/notification paths — the drafts agree on this and on keeping `issue:*` codes rather than renaming (except the UX draft, see issues).
- Every draft ships the four test families plus the new tripwires (forbidden-columns grep on portal projections, lexeme probe on search_index, contact-writable census update, kind-catalog audience test) in the same commit as the feature — matching PLAN.md §2's definition of done.
- Continuity box stays pointer-only and the vault is a separately gated module with server-side envelope encryption; CONTINUITY_BOX.md is not reopened, only SECURITY.md §6 and the DPA wording — the correct scope of change.

### Issues

**[blocker] Portal / data-layer visibility — Project.portalEnabled**  
All three drafts add `Project.portalEnabled` as a gate but disagree on how it reaches the data layer: architecture says 'RESTRICTIVE policy = clientId AND visibility AND project.portalEnabled (or denormalised flag)' (undefined), sequencing says 'denormalise portalEnabled onto work_item/comment via trigger', UX puts it in the projection/portal capability layer only. TENANCY.md §7.2's proven `portal_gate` template is a pure column comparison on `(client_id, visibility)`; a join in a RESTRICTIVE policy is not in the template, and a projection-only gate means a CLIENT_VISIBLE item in a not-yet-enabled project leaks the moment `authorizePortal()` has a bug — exactly the 'worst bug' the standing rule says must be closed at the DATA layer. The sequencing draft's own test ('portalEnabled=false ⇒ zero rows for every table') is unachievable unless the gate also lands on the EXISTING class-B tables (Document, Milestone, ProjectVersion, Service — Milestone is 'client-visible by nature' with no visibility column at all in DATA_MODEL.md).  
*Fix:* Decide one mechanism before the first Phase-2 migration and apply it uniformly to every class-B table with a projectId, including Document/Milestone/ProjectVersion/Service. Recommended: denormalised `portal_enabled boolean NOT NULL DEFAULT false` maintained by an AFTER UPDATE trigger on project (fan-out is bounded per project), added to the `portal_gate` USING clause as `AND portal_enabled`; register it in the model-registry `clientScoped` posture test so a new class-B table without the column fails CI. Alternative (simpler, if acceptable UX): give Project its own `visibility` column (INTERNAL default = portal off) and enforce child ≤ parent up to the project via the same trigger family — but that forces cascading INTERNAL on disable, which loses per-item sharing decisions. Write the choice into TENANCY.md §7.2 as an amendment with the new policy text.

**[blocker] Vault — credential share links & platform-credential reachability**  
The architecture draft says share-link consumption runs 'under withPlatform(system) (no principal) … rendered on the portal host route group without a session', and UX/sequencing render `/portal/share/[token]` as a no-login page. Two violations: (1) TENANCY.md §12 states 'tenant and portal request paths never hold the credential [app_platform, BYPASSRLS] — the bypass is unreachable from them by construction'; a portal route calling withPlatform breaks that invariant. (2) The synthesis §2.8 itself lists 'public no-login share links, magic links' as X (leak surface), yet §2.11 ships a no-login token that reveals a client's WordPress/hosting password — the highest-liability data on the weakest auth path.  
*Fix:* Encode tenantId in the token (`<tenantId>.<random>`; store hash of the random part), resolve via `withTenant(tenantId, {type:'system'})` — the same brokered-write pattern TENANCY §7.2 uses for contact uploads — never withPlatform from a portal/tenant route; add an ESLint import-boundary rule that `getPlatformClient`/`withPlatform` is importable only from `(platform)` and `jobs/`. Require at least one of: recipient is an authenticated Contact of that client, or mandatory email verification (OTP to recipientEmail) — passcode alone is not enough; default `requireEmailVerification=true`, `maxViews=1`, TTL ≤ 7 d, tenant preference to disable external links entirely. Record in SECURITY.md §5/§6 and the DPA.

**[major] Contact-writable census (TENANCY §7.2 / §11) — WorkItem & Comment**  
Drafts disagree on what a contact may write and one design is infeasible: architecture writes a WITH CHECK allowing contact INSERT of WorkItem only when `kind='REQUEST' AND source='PORTAL' AND state_category='TRIAGE'`; UX says the census grows by 'WorkItem (state category of own-assigned items only …)' so a contact can mark an assigned task Done — that UPDATE violates the architecture policy. Also a contact-principal INSERT of WorkItem must supply `stateId` referencing WorkflowState, which is class A (`portal_deny`) — the contact transaction cannot even read the default TRIAGE state. Architecture additionally adds `Notification.readAt` (UPDATE) for contacts. The CI census test currently asserts exactly {Issue, IssueComment, ContinuityOpenRequest, ProjectVersion approval columns}.  
*Fix:* Broker every contact-caused WorkItem write (request creation, task completion) through `withTenant(tenantId, {type:'system'})` after `authorizePortal()` — the sanctioned pattern — so WorkItem stays out of the contact-writable set entirely. Keep the census to exactly: Comment (INSERT, WITH CHECK `visibility='CLIENT_VISIBLE' AND client_id=app.client_id AND author_contact_id=app.principal_id`), ProjectVersion approval columns, Document approval columns (if adopted), Notification.readAt/archivedAt (contact receiver rows), ContinuityOpenRequest. Land the `app.principal_id` GUC in withTenant (architecture Phase 2) since two of those policies need it. Update TENANCY.md §7.2 table and the census test in the same commit as the policies.

**[major] Time — ProjectTimeSummary shape**  
UX draft: 'ProjectTimeSummary is a projection (SQL view / read model), not a table'. Under FORCE RLS a view over `time_entry` (class A, `portal_deny`) returns zero rows to a contact principal, so the portal hours widget would need a system-principal read inside a portal path — which the architecture draft explicitly forbids ('no system-principal bypass in any portal path'). Sequencing is ambiguous ('projection'). Only the architecture draft's physical class-B table (upserted in the entry transaction, nightly self-heal, no member ids by construction) satisfies 'visibility enforced at the data layer'.  
*Fix:* Adopt the physical `ProjectTimeSummary` table (class B, `(tenantId, projectId, periodMonth)` unique, visibility derived from `hoursSharingMode`, portal_gate + portal_enabled), plus the property test 'summary == SUM(time_entry) after random writes' and 'no member id column'. Reject the view approach in DATA_MODEL.md with one line so it is not re-proposed.

**[major] Work — WorkflowState is class A; portal cannot join it**  
UX and sequencing drafts say the portal maps 'state names → category labels server-side; the state table is never selected' — but under a contact principal WorkflowState (class A) yields zero rows, so an `include: {state}` returns null and the mapping cannot happen without a bypass. Only the architecture draft denormalises `stateCategory` onto WorkItem (with an immutable-category trigger). Same problem for `assigneeMemberId` → Member (class A): the UX portal page shows 'assignee name only if tenant allows', which is unresolvable under RLS.  
*Fix:* Adopt architecture's `WorkItem.stateCategory` denormalisation (kept in sync by the state-machine service + trigger; index `(tenantId, clientId, visibility, stateCategory)`), and make it the only state field portal projections read. Drop assignee names from portal v1 (or store a denormalised `assigneeDisplayName` written by the service — decide explicitly; recommend drop). Add the same rule to the search_index feed.

**[major] Module keys / permission namespace / entitlements schema**  
Drafts propose 3 (architecture: work,time,vault), 4 (UX: +intake, renaming `issues`), or 5 (sequencing: +budgets,+assets) module keys. AUTHZ.md §5 and ARCHITECTURE.md §3 fix a 1:1 rule: entitlement key = Permission.module = `src/modules/<key>` folder = `module.<key>.enabled` preference; `entitlementsSchema.modules` in src/entitlements/resolver.ts is `schemaVersion: 1` with the seven fixed keys. Renaming `issues`→`intake` or deleting the five `issue:*` codes (UX D2) contradicts AUTHZ §3.1 'codes are immutable forever; deprecate and add' and would delete RolePermission rows in the already-provisioned tenant zero. Splitting `budgets`/`assets` from `time`/`vault` creates folders nobody will sell separately.  
*Fix:* Adopt three keys (`work`, `time`, `vault`); keep `issues` in the schema (deprecated, unseeded at TEMPLATE_VERSION 2 via platform migration of system roles per AUTHZ §3.5) and keep the `issue:*` codes with 'deprecated' descriptions. Bump `entitlementsSchema.schemaVersion` to 2 when adding keys and give the parser a v1→v2 upgrade path (defaults on). Put portal-control codes (`project:manage_portal`, `hoursSharingMode`) under module `portal`, `project_update:*` under `work`; record in AUTHZ §3.2 and ARCHITECTURE §3.

**[major] MFA policy — ✦ on employee-seeded codes**  
All drafts seed `credential:reveal` (and UX seeds `time`-module codes) with ✦ `requiresMfa` on templates that include Employee. AUTHZ.md §7.5 says assigning any role whose set includes a ✦ permission forces MFA enrolment for the holder; SECURITY.md §3.5 says all non-owner members have MFA 'available', tenant-enforced MFA is v2 (OPEN_QUESTIONS C16). Enabling the vault module therefore silently makes every employee MFA-mandatory — probably desirable ('MFA required to reveal at all') but it reverses a documented decision and the ✦-never-auto-propagates rule means custom clones won't receive `credential:reveal` at all.  
*Fix:* Make it an explicit dated decision (OPEN_QUESTIONS decision 13): either (a) accept employee MFA enrolment as a consequence of the vault entitlement and update SECURITY.md §3.5 + C16, or (b) seed `credential:reveal` CMA only and let tenants grant it to employees deliberately. Extend AUTHZ §7.5's step-up list (currently 3 codes) with the new ✦ set and put `requireRecentMfa()` in Phase 1b as every draft assumes.

**[major] Search — Sweden-specific TS config in a one-way-door table**  
`search_index.search tsvector GENERATED … config 'fortleva' = unaccent + swedish_stem` hardcodes Swedish stemming for every tenant and every language, including Naxdor's US clients and any English-only tenant. PLAN.md §2 rules: 'nothing Naxdor-specific in schema', 'no assumption of exactly two languages'. The drafts list this as a one-way door, which makes baking the bias in worse.  
*Fix:* Store a `lang regconfig` (or text) column per search_index row derived from tenant default locale (later per-project/document language) and generate `to_tsvector(lang, …)` — `to_tsvector(regconfig, text)` is IMMUTABLE so the STORED generated column still works; ship `fortleva_sv` and `fortleva_en` (unaccent + swedish/english stem) configs and default by `Tenant.defaultLocale`. Keep the trigram fallback language-neutral.

**[major] Rates — cost-rate storage differs across drafts; encryption inventory is 'closed'**  
Architecture: cost amount encrypted on an immutable RateCard row, entry stores `costRateCardId` only. UX: `costRateEnc` encrypted on every TimeEntry. Sequencing: `amountEnc` on RateCard, resolved at read. Fanning salary-grade data across every entry row (UX) multiplies exposure and contradicts the synthesis's own risk note. Also DATA_MODEL.md §4 and SECURITY.md §6 declare the encryption inventory a closed, one-way-door list; none of the drafts add a dated inventory entry for RateCard.amount, CredentialSecret, TOTP seeds, push keys.  
*Fix:* Adopt architecture: immutable RateCard rows (change = close + insert), `amountCiphertext` on COST cards only, Prisma `omit` globally, decrypt only in rates.ts behind `rate:view_cost` + recent MFA, aggregate as SUM(seconds) GROUP BY cost card. Add a dated §4/§6 inventory table update listing every new encrypted field with AAD context; note the v2 root stays the env keyring (no KMS) — a deviation from SECURITY §6's 'v2 selects a per-tenant DEK wrapped by KMS' seam that should be stated.

**[major] Phase placement contradictions**  
(1) Notification/EmailOutbox tables: architecture lands shapes + `notify.emit()` in 2W, sequencing lands Notification in W2 with outbox in P5, UX lands everything in P5 — yet timer nudges/auto-stop/budget alerts (time phase) need at least in-app notifications and budget alerts want email. (2) ProjectUpdate: architecture 2T, UX and sequencing Phase 3. (3) UX runs Phase 5 before Phase 4; the other two keep 4 before 5.
