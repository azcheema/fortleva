# RUNBOOK.md — Operating and self-hosting Fortleva

> **Status:** skeleton, opened 2026-08-17 (Phase 2 close-out; owed since Phase 1b). Kept current every phase — this is the credibility artifact behind `CONTINUITY_BOX.md` §10.2 ("you could run this without me" must be checkable). Sections marked *(TODO)* are headings with a one-line intent until the phase that fills them lands. Product decisions live in the other docs; this file is only *how to run it*.

## 0. What you are running

One Next.js 16 app (App Router, `src/app`) serving three planes on two hosts (`ARCHITECTURE.md` ARC-11): tenant + portal on `APP_URL`, the platform console on `OPS_URL`. Postgres (Neon today; any Postgres ≥ 15 with RLS works), S3-compatible object storage (Cloudflare R2, EU jurisdiction; any S3 works — the transport is `src/storage`), Better Auth for identity, next-intl for sv/en. No queue, no cache, no third daemon in v1. Jobs are plain functions under `src/jobs/` invoked by cron (Vercel Cron in production; `pnpm tsx` locally).

## 2. Database: roles, migrations, RLS

- **Three roles** (`TENANCY.md` §6.1): the owner (migrations only), `app_runtime` (RLS enforced; the app), `app_platform` (BYPASSRLS; console + jobs). Migration `20260808191500_security_foundations` creates the roles and policies; grants are re-asserted by every later migration that adds a table. A fresh Postgres needs the two roles to exist with passwords before `DATABASE_URL` / `PLATFORM_DATABASE_URL` can point at them.
- **Migrate:** `pnpm prisma migrate deploy` (uses `DIRECT_URL`). Never `migrate reset` / `db push` against a database with data. Every migration is hand-reviewed SQL under `prisma/migrations/`; RLS policies, triggers and role grants live there, not in the schema file.
- **Seed:** `pnpm prisma db seed` runs `prisma/seed.ts` — the permission catalog (~~**98** codes at TEMPLATE_VERSION 5~~ ~~**104** codes at TEMPLATE_VERSION 7 since 2026-10-01~~ ~~**108** codes at TEMPLATE_VERSION 9 since 2026-10-03 (105 / TV8 on 2026-10-02 — slice 84, which did not update this line)~~ ~~**109** codes at TEMPLATE_VERSION 10 since 2026-10-04 (slice 90, `credential:share` ✦ — it reaches the owner, manager and admin SYSTEM roles only, so until the seed runs on a tenant nobody there can make a share link)~~ **112** codes at TEMPLATE_VERSION 13 since 2026-10-06 (corrected by slice 95: slices 91 and 92 did not update this line — 110 / TV11 `credential:change_visibility`, 111 / TV12 `credential:unseal`; slice 95 adds `credential:export` ✦, owner template only, so until the seed runs on a tenant nobody there can export its logins), `src/authz/catalog.ts` — *corrected 2026-09-21; this said 63, the TV1 figure, three catalog bumps later. AUTHZ.md §3.2's running-count paragraph is normative and `catalog.test.ts` pins it*) and B3 additive template propagation into existing tenants' system roles (`runTemplatePropagation`). Idempotent. **THE SEED IS PART OF THE RELEASE, NOT A SETUP STEP — and since 2026-09-21 skipping it can make a SAFETY CONTROL unreachable.** A permission code exists only as a `Permission` row the seed upserts, and a role holds it only after `runTemplatePropagation` grants it at the current `TEMPLATE_VERSION`; there is no migration. Phase 3 slice 4 moved the portal master switch (`setPortalEnabled` — the emergency "stop showing this client our data" control, TENANCY.md §7.2) from `project:edit`, which every template holds, to the new `project:manage_portal`. **Between deploying that commit and running this seed, nobody in any tenant holds the code**, so the Portal tab is hidden and the switch throws FORBIDDEN. Nothing becomes newly visible to a client in that window — a project already sharing goes on sharing — but it cannot be stopped from the UI until the seed runs. CI runs it (`ci.yml`), so no gate can catch a deploy that does not: **run `pnpm exec tsx prisma/seed.ts` with every release that bumps `TEMPLATE_VERSION`, before announcing it.** **Tenant keys (Phase 3V, 2026-10-01): the seed back-fills an envelope key for every tenant that has none ONLY when asked — `TENANT_KEY_BACKFILL=1` — once, on the release that ships the vault, from a shell with the deployment's `DIRECT_URL`, `FIELD_ENCRYPTION_KEY` and `FIELD_ENCRYPTION_KEY_ID` exported.** It mints NOTHING unless this process's root keyring unwraps the newest tenant keys already in the database AND at least one of them is wrapped under this shell's ACTIVE root key id — the key a mint would use — which is the proof that the shell holds the deployment's key. Do not run it from a shell set up for a root-key rotation (new key active, old one as `_PREVIOUS`) before the deployment has the new key: it refuses, by design. So on a database with no tenant key yet it refuses by design: let the application mint the first one (any first credential, or a cost rate, in any tenant), then run it. A wrong key — a developer's `.env.local` against production, say — refuses before a single key is written. Never set the variable in CI or in `neon-smoke.yml`. Not running it costs no correctness: a tenant's key is minted on its first encrypt anyway, and a tenant with nothing encrypted has nothing a rotation or a re-wrap could touch. Close a PowerShell session you exported the key in afterwards (`$env:` variables live as long as it does). It does **not** create feature flags, and it does **not** create a tenant: tenant zero comes from `pnpm exec tsx scripts/seed-naxdor.ts` (`scripts/seed-naxdor.ts:58-67`), which is for an empty database only. *(Corrected 2026-08-19 — this line previously claimed feature flags and tenant zero; `prisma/seed.ts` is 68 lines and does neither.)*
- **Verify posture after any migration:** `pnpm test:db` (runs as the real `app_runtime` role; a superuser false-passes RLS). The registry posture test (`src/db/isolation.dbtest.ts`) fails if a tenant table lacks its policies; `src/db/model-registry.test.ts` fails if a model is unclassified; `src/export/manifest.test.ts` fails if a tenant model is missing from the export census.
- **Neon specifics:** the pooler is PgBouncer in transaction mode — GUCs are set with `set_config(..., true)` (transaction-local) by `withTenant()`; do not add session-level `SET`s. Branching is fine for previews; production is the `main` branch. *(TODO: PITR window + how to restore a branch to a point in time.)*

## 3. Storage: buckets, keys, migration to any S3

- Two buckets are planned: general (documents, exports) and continuity (sealed boxes, bucket lock; Phase 8). Keys are opaque `<tenantId>/<fileObjectId>`; the DB row (`FileObject`) is the source of truth for existence, size, sha256, kind.
- Uploads never pass through the app (presigned PUT with signed `Content-Length` + `Content-Type`, HEAD-verified on commit). Downloads are presigned GETs with `Content-Disposition: attachment`, off-origin. Server-produced blobs (tenant export zips) are written with `putObject()`.
- **R2 → any S3:** copy objects key-for-key (`rclone sync`), point the four `R2_*` variables (and the endpoint builder in `src/config`) at the new endpoint. No key rewrite is needed; `FileObject.r2Key` is endpoint-agnostic.
- Reconciliation: `src/jobs/expire-pending-uploads.ts` releases stale PENDING reservations — run by the hourly job (`/api/jobs/run`) since slice 122, for uploads presigned a day ago and never committed (the row becomes DELETED and its bytes, if any, are removed). *(TODO: bucket↔DB orphan sweep once R2 env exists.)*

## 5. Key material

- **Root key** (`FIELD_ENCRYPTION_KEY`, id `FIELD_ENCRYPTION_KEY_ID`): wraps every per-tenant DEK (`TenantKey`). Stored only in the deployment's secret store (Vercel env) and in the founder's Bitwarden vault with Emergency Access configured (`CONTINUITY_BOX.md` §10.3). **No key ⇒ no decryption of (among others — `SECURITY.md` §6.2 is the inventory, this is not) `Tenant.iban/bic/bankgiro/plusgiro` and (from Phase 3V) every vault credential.** *(`TwoFactor.secret` was listed here; it is Better Auth's, under `BETTER_AUTH_SECRET` — next bullet.)* Exports deliberately omit these columns for that reason.
- **Rotation:** set the new key as `FIELD_ENCRYPTION_KEY`/`_ID`, the old one as `FIELD_ENCRYPTION_KEY_PREVIOUS`, deploy, run the re-wrap job *(TODO: job not built yet — `SECURITY.md` §6 rotation lands with 3V)*, then drop `_PREVIOUS`.
- **Better Auth secret (`BETTER_AUTH_SECRET`)** *(rewritten 2026-09-24, slice 58 — this line said "rotating signs everyone out; no data loss", which is false)*. Better Auth encrypts every TOTP secret and backup code under it, so it is key material, not just a signing secret.
  - **Do not replace it as routine hygiene.** After a swap no factor decrypts: every member with 2FA is locked out, and so is the console's sole operator, whose factor is the only way in. To sign everyone out, delete sessions instead (§8).
  - **Never set `BETTER_AUTH_SECRETS`**, Better Auth 1.6's versioned list, as a gentler rotation. When it is set, its first entry REPLACES every instance's `secret` (`context/create-context.mjs`) — the portal's `portalAuthSecret` included, which silently puts the portal back on the shared secret that `src/config` explains it must not share — and the existing `TwoFactor` rows carry no version envelope, so they decrypt only through the old single value anyway. Nothing here has tested it.
  - **If it has LEAKED, replace it anyway: the factors are lost either way.** Whoever holds it can sign an email-verification link for any address — which on the member plane, since C30, confirms an unverified account only together with that account's PASSWORD (the confirmation page checks both; before C30 the link alone confirmed it and signed the person in), so in practice it confirms addresses the holder signed up themselves, without their mailboxes; with a database read as well, it forges the cookie of every live session (`session.token` is stored plain; the cookie is that token and an HMAC under this secret), the console's factor-stamped sessions included, and decrypts every seed. So, in order: (1) set a new value and redeploy — the portal's derived secret changes with it, ending every portal session; (2) as `app_runtime` (see §8), reset every factor: `DELETE FROM two_factor; UPDATE "user" SET two_factor_enabled = false;` — both statements, `SECURITY.md` §3.5 says why the second is not optional; (3) sign everyone out, trusted devices included (§8); (4) remove any account the holder may have made — nothing records when an address was CONFIRMED (`"user".updated_at` is only a proxy for it) and `app_runtime` cannot see memberships, so list every user created or updated during the exposure (`SELECT email, created_at, updated_at FROM "user" WHERE updated_at >= $1;`) and, for each one nobody can vouch for, run §8's statement for **an account somebody else signed up** (the one with no `email_verified` filter: the holder can confirm their own sign-ups, so the other statement would miss them). The membership foreign key refuses it for anybody already in a workspace, which is the membership check; those are founder decisions; (5) members re-enrol at `/account`, and every sign-up link still in somebody's inbox is dead — those people sign in with their password and are mailed a fresh one (C30; three an hour); and the operator re-enrols through `/ops/login`'s ramp **at once**, because until then the console opens with the password alone (`SECURITY.md` §3.5, the bounded window).
  - **Custody: keep it like the root key**, because it is key material now — an offline copy beside `FIELD_ENCRYPTION_KEY`'s (`CONTINUITY_BOX.md` §10.3). Lose it with no copy and the effect is the leaked case's step (2) without the choice. Whether that copy exists today is not recorded here; check it. The keyring's restore drill (`SECURITY.md` §11) does not cover it.

8. **Disconnecting** stops sending at once (it is the kill switch); to remove Fortleva from Fortnox entirely, a system administrator removes it in Fortnox under *Manage integrations*. **The platform-wide kill switch** is `FORTNOX_TRANSPORT` unset. *(Slice 114c, C90 (c), (d):)* after a disconnect, the entries already in a Fortnox file and not yet sent wait on the Bookkeeping page's **Waiting for you** card: each file's never-sent entries download as an SIE of just those (oldest file first; then again from the file's row, "Not sent (SIE)" — import it ONCE), any of them can be marked **Booked by hand**, and one whose answer never came says where to look in Fortnox and is marked Booked by hand or **Not in Fortnox**; a later connection — even to the same company — never sends them. With the transport unset the connected company's NEW entries still go in no file at all until an owner disconnects (the security review of 114b, its 2) — so unsetting it is a pause, and a long one should be a disconnect. **No `live`, sandbox included, outside throwaway workspaces, before step 11 (a)–(c) are confirmed** — and production waits for Fortnox's written consent anyway (step 1).
9. **A company "already connected to another workspace"** (only one live connection per Fortnox company): the other workspace's owner disconnects it. If that workspace is gone or its owners unreachable, support marks its row DISCONNECTED — the platform role, in one audited transaction (a `platform.system_job` row naming the workspace and the reason), never a hand-typed `DELETE`.
10. **The nightly send** *(slice 114b)* runs in `POST /api/jobs/run` (45 seconds a run): for each connected workspace it books what is owed, in order, and — once the workspace's day has turned and nothing is owed — makes the night's file of the connected company's new entries and sends it. **Once connected, those entries go to Fortnox ONLY**: Make file offers only another company's (an org. number the connection is not), and a Fortnox file's SIE is never downloadable (importing it too would book twice). A stop is shown on the Bookkeeping page (which entry, why, Fortnox's own words); it retries every run, except a consent removed, a licence gone or a changed company, which wait for an owner's reconnect. *(Slice 114c, C89 (c), (e), C90 (a), (b):)* the workspace's **owners are told** — once per stop, then every **Monday at 08:00** workspace time while it lasts (inbox, and email as each owner's email setting allows), and a note in their inbox when it works again. The entry a stop is at can be marked **Booked by hand** on the page (only that one — Fortleva sends every other by itself), and a voucher whose PDF never attached, a day on, **PDF attached by hand**.
11. **To check on the sandbox before production** (each UNCONFIRMED in Fortnox's documentation; the client in `src/integrations/fortnox/live.ts` follows the research in the design doc §0): (a) `POST /3/vouchers?financialyear=` answers `{"Voucher":{"VoucherNumber",…}}` and takes amounts as JSON numbers with two decimals; (b) `GET /3/voucherseries/F?financialyear=` gives `NextVoucherNumber` (a reconcile starts there); (c) `GET /3/vouchers/F/{n}?financialyear=` gives the voucher's `Comments` (the marker `Fortleva <entry id>`); (d) `POST /3/inbox?path=inbox_v` (multipart `file`) answers `{"File":{"Id"}}`, and `POST /3/voucherfileconnections?financialyear=` connects it — one file to one voucher; (e) what Fortnox answers for a locked period, an inactive account and a series not manual (today they show as "Fortnox said: …"). Book a handful into a sandbox company, check them in Bokföring → Verifikationer, then delete the sandbox company. **(a)–(c) are what "never booked twice" rests on** (a lost answer is looked for by number and, when not found, asked again — the security review of 114b, its 4): confirm them before `live` anywhere, and that `NextVoucherNumber` moves on the moment a voucher is made.
12. **A voucher whose answer was lost** (a timeout): it is SENDING on the page until a later run finds it by number — never booked twice. If a disconnect came in between, the page says where to look (series F from the number it shows, the comment `Fortleva <ref>`): found → Booked by hand; not there → Not in Fortnox, and it downloads with the rest (slice 114c).

## 12. Releasing a change to production *(added 2026-10-15, slice 122's review)*

Every push to `main` builds a production deployment on Vercel, and nothing serves it until it is promoted (§11 step 7). Claude says in each slice's report whether it carries a database migration or a new `TEMPLATE_VERSION`. The routine:

1. **CI is green** on that commit (GitHub → Actions).
2. **If the slice has a migration:** a PowerShell window (§11's rule) with `$env:DIRECT_URL` = the production owner URL → `pnpm exec prisma migrate status` (names production, lists the new migration) → `pnpm exec prisma migrate deploy`.
3. **If the slice raised `TEMPLATE_VERSION`** (a new permission code): in the same window, `pnpm exec prisma db seed` — until it runs, the new code is refused to everyone.
4. **Promote** the deployment (Vercel → Deployments → it → Promote). A changed environment variable reaches nothing until a deployment is BUILT with it: Redeploy, then Promote.
5. **The first time a push is NOT promoted**, check Vercel → Logs for `/api/jobs/outbox`: its calls must still come from the PROMOTED deployment (Vercel Cron calls the current production deployment; this confirms it once).

Migrations are written additive-first (a new column or table before the code that needs it), so the deployment still serving keeps working between steps 2 and 4. To go back: promote the previous deployment — a migration is never reversed by hand (AGENTS.md).
