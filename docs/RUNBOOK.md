## 0. What you are running

One Next.js 16 app (App Router, `src/app`) serving three planes on two hosts (`ARCHITECTURE.md` ARC-11): tenant + portal on `APP_URL`, the platform console on `OPS_URL`. Postgres (Neon today; any Postgres ≥ 15 with RLS works), S3-compatible object storage (Cloudflare R2, EU jurisdiction; any S3 works — the transport is `src/storage`), Better Auth for identity, next-intl for sv/en. No queue, no cache, no third daemon in v1. Jobs are plain functions under `src/jobs/` invoked by cron (Vercel Cron in production; `pnpm tsx` locally).

## 1. Environment variables

Every variable is read in exactly one place (`src/config/index.ts` for hosts/mail/storage/limits, `src/db/client.ts` for database roles, `src/crypto/root-keyring.ts` for key material). Nothing else touches `process.env`.

| Variable | Required | Read by | Purpose |
|---|---|---|---|
| `APP_URL` | prod | `src/config` | Canonical tenant/portal origin (`https://os.naxdor.com` today). All absolute URLs, cookies (`__Host-flv.<plane>`), Better Auth `baseURL`. |
| `OPS_URL` | prod | `src/config` | Platform-console origin. Falls back to `APP_URL` in dev. |
| `DATABASE_URL` | yes | `src/db/client.ts` | **Pooled** connection as `app_runtime` (RLS enforced, no BYPASSRLS). All tenant/portal work. |
| `PLATFORM_DATABASE_URL` | prod | `src/db/client.ts` | Pooled connection as `app_platform` (BYPASSRLS — every use audited via `withPlatform()`). Platform console + jobs. |
| `DIRECT_URL` | migrate | `prisma.config.ts` | **Unpooled owner** connection for `prisma migrate` and seed only. Never used at runtime. |
| `BETTER_AUTH_SECRET` | yes | Better Auth | Signs every cookie and emailed verification link, seeds the portal's own secret (`portalAuthSecret`), **and is the key every TOTP secret and backup code is encrypted under** — Better Auth encrypts `TwoFactor` itself; `FIELD_ENCRYPTION_KEY` never touches it *(corrected 2026-09-24, slice 58 — this row said only "session/cookie signing; rotating it signs everyone out")*. **Read §5 before changing it.** Never set `BETTER_AUTH_SECRETS` (§5). |
| `FIELD_ENCRYPTION_KEY`, `FIELD_ENCRYPTION_KEY_ID` | yes | `src/crypto/root-keyring.ts` | Root key (base64, 32 bytes) + id that wraps every tenant DEK (`TenantKey.wrappedDek`). **Losing it loses every encrypted column.** *(It does NOT encrypt the TOTP secret, which this row used to claim — `BETTER_AUTH_SECRET` does.)* See §5. |
| `FIELD_ENCRYPTION_KEY_PREVIOUS` | rotation | `src/crypto/root-keyring.ts` | Previous root key during a rotation window (`<id>:<base64>`). |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` | prod | `src/config` → `src/storage/r2.ts` | Object storage. All four present ⇒ R2 transport at `https://<account>.eu.r2.cloudflarestorage.com`; absent ⇒ local-disk dev transport (`.dev-storage/`, refuses production). Any S3 endpoint works with a one-line change to the endpoint builder in `src/config`. |
| `DEV_STORAGE_SECRET` | dev | `src/config` | HMAC secret for the dev transport's signed URLs (falls back to `BETTER_AUTH_SECRET`). |
| `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` | prod (recommended) | `src/config` → `src/ratelimit` | Sliding-window rate limits on sign-in / sign-up / invite-accept / step-up. Absent ⇒ **fail-open no-op**, logged once at boot. |

Local dev: copy the values into `.env.local` (git-ignored). `prisma.config.ts` loads `.env.local` then `.env` for the CLI; Next loads them itself at runtime.

## 2. Database: roles, migrations, RLS

- **Three roles** (`TENANCY.md` §6.1): the owner (migrations only), `app_runtime` (RLS enforced; the app), `app_platform` (BYPASSRLS; console + jobs). Migration `20260808191500_security_foundations` creates the roles and policies; grants are re-asserted by every later migration that adds a table. A fresh Postgres needs the two roles to exist with passwords before `DATABASE_URL` / `PLATFORM_DATABASE_URL` can point at them.
- **Migrate:** `pnpm prisma migrate deploy` (uses `DIRECT_URL`). Never `migrate reset` / `db push` against a database with data. Every migration is hand-reviewed SQL under `prisma/migrations/`; RLS policies, triggers and role grants live there, not in the schema file.
- **Seed:** `pnpm prisma db seed` runs `prisma/seed.ts` — the permission catalog (**98** codes at TEMPLATE_VERSION 5, `src/authz/catalog.ts` — *corrected 2026-09-21; this said 63, the TV1 figure, three catalog bumps later. AUTHZ.md §3.2's running-count paragraph is normative and `catalog.test.ts` pins it*) and B3 additive template propagation into existing tenants' system roles (`runTemplatePropagation`). Idempotent. **THE SEED IS PART OF THE RELEASE, NOT A SETUP STEP — and since 2026-09-21 skipping it can make a SAFETY CONTROL unreachable.** A permission code exists only as a `Permission` row the seed upserts, and a role holds it only after `runTemplatePropagation` grants it at the current `TEMPLATE_VERSION`; there is no migration. Phase 3 slice 4 moved the portal master switch (`setPortalEnabled` — the emergency "stop showing this client our data" control, TENANCY.md §7.2) from `project:edit`, which every template holds, to the new `project:manage_portal`. **Between deploying that commit and running this seed, nobody in any tenant holds the code**, so the Portal tab is hidden and the switch throws FORBIDDEN. Nothing becomes newly visible to a client in that window — a project already sharing goes on sharing — but it cannot be stopped from the UI until the seed runs. CI runs it (`ci.yml`), so no gate can catch a deploy that does not: **run `pnpm exec tsx prisma/seed.ts` with every release that bumps `TEMPLATE_VERSION`, before announcing it.** It does **not** create feature flags, and it does **not** create a tenant: tenant zero comes from `pnpm exec tsx scripts/seed-naxdor.ts` (`scripts/seed-naxdor.ts:58-67`), which is for an empty database only. *(Corrected 2026-08-19 — this line previously claimed feature flags and tenant zero; `prisma/seed.ts` is 68 lines and does neither.)*
- **Verify posture after any migration:** `pnpm test:db` (runs as the real `app_runtime` role; a superuser false-passes RLS). The registry posture test (`src/db/isolation.dbtest.ts`) fails if a tenant table lacks its policies; `src/db/model-registry.test.ts` fails if a model is unclassified; `src/export/manifest.test.ts` fails if a tenant model is missing from the export census.
- **Neon specifics:** the pooler is PgBouncer in transaction mode — GUCs are set with `set_config(..., true)` (transaction-local) by `withTenant()`; do not add session-level `SET`s. Branching is fine for previews; production is the `main` branch. *(TODO: PITR window + how to restore a branch to a point in time.)*
- **Any-Postgres restore** (`CONTINUITY_BOX.md` §10.2): `pg_dump` from Neon → `pg_restore` into the target → create the two roles → point the three URLs → `migrate deploy` (no-op if current) → seed (idempotent). *(TODO: rehearse once and record timings.)*

## 3. Storage: buckets, keys, migration to any S3

- Two buckets are planned: general (documents, exports) and continuity (sealed boxes, bucket lock; Phase 8). Keys are opaque `<tenantId>/<fileObjectId>`; the DB row (`FileObject`) is the source of truth for existence, size, sha256, kind.
- Uploads never pass through the app (presigned PUT with signed `Content-Length` + `Content-Type`, HEAD-verified on commit). Downloads are presigned GETs with `Content-Disposition: attachment`, off-origin. Server-produced blobs (tenant export zips) are written with `putObject()`.
- **R2 → any S3:** copy objects key-for-key (`rclone sync`), point the four `R2_*` variables (and the endpoint builder in `src/config`) at the new endpoint. No key rewrite is needed; `FileObject.r2Key` is endpoint-agnostic.
- Reconciliation: `src/jobs/expire-pending-uploads.ts` releases stale PENDING reservations (call from cron; not scheduled yet). *(TODO: bucket↔DB orphan sweep once R2 env exists.)*

## 5. Key material

- **Root key** (`FIELD_ENCRYPTION_KEY`, id `FIELD_ENCRYPTION_KEY_ID`): wraps every per-tenant DEK (`TenantKey`). Stored only in the deployment's secret store (Vercel env) and in the founder's Bitwarden vault with Emergency Access configured (`CONTINUITY_BOX.md` §10.3). **No key ⇒ no decryption of (among others — `SECURITY.md` §6.2 is the inventory, this is not) `Tenant.iban/bic/bankgiro/plusgiro` and (from Phase 3V) every vault credential.** *(`TwoFactor.secret` was listed here; it is Better Auth's, under `BETTER_AUTH_SECRET` — next bullet.)* Exports deliberately omit these columns for that reason.
- **Rotation:** set the new key as `FIELD_ENCRYPTION_KEY`/`_ID`, the old one as `FIELD_ENCRYPTION_KEY_PREVIOUS`, deploy, run the re-wrap job *(TODO: job not built yet — `SECURITY.md` §6 rotation lands with 3V)*, then drop `_PREVIOUS`.
- **Better Auth secret (`BETTER_AUTH_SECRET`)** *(rewritten 2026-09-24, slice 58 — this line said "rotating signs everyone out; no data loss", which is false)*. Better Auth encrypts every TOTP secret and backup code under it, so it is key material, not just a signing secret.
  - **Do not replace it as routine hygiene.** After a swap no factor decrypts: every member with 2FA is locked out, and so is the console's sole operator, whose factor is the only way in. To sign everyone out, delete sessions instead (§8).
  - **Never set `BETTER_AUTH_SECRETS`**, Better Auth 1.6's versioned list, as a gentler rotation. When it is set, its first entry REPLACES every instance's `secret` (`context/create-context.mjs`) — the portal's `portalAuthSecret` included, which silently puts the portal back on the shared secret that `src/config` explains it must not share — and the existing `TwoFactor` rows carry no version envelope, so they decrypt only through the old single value anyway. Nothing here has tested it.
  - **If it has LEAKED, replace it anyway: the factors are lost either way.** Whoever holds it can sign an email-verification link for any address — which on the member plane, since C30, confirms an unverified account only together with that account's PASSWORD (the confirmation page checks both; before C30 the link alone confirmed it and signed the person in), so in practice it confirms addresses the holder signed up themselves, without their mailboxes; with a database read as well, it forges the cookie of every live session (`session.token` is stored plain; the cookie is that token and an HMAC under this secret), the console's factor-stamped sessions included, and decrypts every seed. So, in order: (1) set a new value and redeploy — the portal's derived secret changes with it, ending every portal session; (2) as `app_runtime` (see §8), reset every factor: `DELETE FROM two_factor; UPDATE "user" SET two_factor_enabled = false;` — both statements, `SECURITY.md` §3.5 says why the second is not optional; (3) sign everyone out, trusted devices included (§8); (4) remove any account the holder may have made — nothing records when an address was CONFIRMED (`"user".updated_at` is only a proxy for it) and `app_runtime` cannot see memberships, so list every user created or updated during the exposure (`SELECT email, created_at, updated_at FROM "user" WHERE updated_at >= $1;`) and, for each one nobody can vouch for, run §8's statement for **an account somebody else signed up** (the one with no `email_verified` filter: the holder can confirm their own sign-ups, so the other statement would miss them). The membership foreign key refuses it for anybody already in a workspace, which is the membership check; those are founder decisions; (5) members re-enrol at `/account`, and every sign-up link still in somebody's inbox is dead — those people sign in with their password and are mailed a fresh one (C30; three an hour); and the operator re-enrols through `/ops/login`'s ramp **at once**, because until then the console opens with the password alone (`SECURITY.md` §3.5, the bounded window).
  - **Custody: keep it like the root key**, because it is key material now — an offline copy beside `FIELD_ENCRYPTION_KEY`'s (`CONTINUITY_BOX.md` §10.3). Lose it with no copy and the effect is the leaked case's step (2) without the choice. Whether that copy exists today is not recorded here; check it. The keyring's restore drill (`SECURITY.md` §11) does not cover it.
- **R2 / Upstash / Neon credentials:** rotate at the provider, update env, redeploy. The runtime R2 credential must never gain delete rights on the continuity bucket (INV-10).

## 7. Browser tests (the e2e harness)

Added 2026-08-17. The unit and DB suites cannot see a control that lies about the database or a theme re-applied on mount — both were real founder-reported bugs. This suite runs the real app in a real browser and exists to catch that class.

- **Run:** `pnpm test:e2e` (headless, list reporter + HTML report) or `pnpm test:e2e:ui`. First run needs the browser once: `pnpm exec playwright install chromium` (~700 MB on disk; chromium + headless shell only — no other engine, and on Linux add `--with-deps` for the OS packages).
- **The server is not yours to start.** `playwright.config.ts` runs `pnpm build && pnpm start` itself on `http://127.0.0.1:3000` with `APP_URL` pinned to that origin — Better Auth pins `baseURL`/`trustedOrigins` to `APP_URL` (INV-D2), so a foreign origin makes every sign-in POST fail as cross-origin. It is a production build on purpose: `next dev` double-mounts under Strict Mode and would mask exactly the mount-time bugs this suite hunts. Locally an already-running server on that port is reused; in CI it never is. Env comes from `.env.local` / `.env` (§1) — the same secrets the app and `pnpm test:db` need.
- **What it covers** (one worker, serialised, ~6 min cold): `e2e/theme.spec.ts` (the light/dark preference survives navigation, reload and every later mount of the toggle, with the OS scheme emulated both ways), `e2e/visibility.spec.ts` (a document's visibility control agrees with the stored row in both directions, on `/files` and on the client Files tab, and a failed change says so instead of looking like a silent revert), and `e2e/visual.spec.ts` (§ `UI.md` 10.14 — 48 stops × light/dark × desktop/mobile = 192 screenshots to `.design-shots/` (written locally only — CI skips the file write, nothing there reads them), plus a per-stop DOM audit: one `h1`, no invisible text, no untranslated keys, no horizontal overflow at 390 px, no console errors or failed requests).
- **Fixtures — the data-safety contract** (`e2e/fixtures/tenant.ts`, `e2e/fixtures/seed-cli.ts`): `global-setup` provisions a throwaway tenant with slug `e2e-<random>` through the ordinary `provisionTenant()`, an owner at `@test.invalid` whose password is generated per run and passed to the fixture process in an env var (never written to a file, never printed), and a workspace to photograph — clients (one archived, one long-named), projects across three statuses, contacts, services, milestones, documents at every visibility, a pending invitation. ## 8. Incident quick reference *(TODO)*

- Kill-switch a module for one tenant or all: `FeatureFlag` row (`module.<key>`, `tenantOverrides`) — gate 1 in `src/entitlements/resolver.ts`.
- Suspend a tenant / a member: platform console (`tenant.suspended`, `member.suspended` audit events).
- **Sign everyone out** *(rewritten 2026-09-24 — this said "rotate `BETTER_AUTH_SECRET`", which also destroys every second factor, §5)*: `DELETE FROM session; DELETE FROM contact_session; DELETE FROM verification WHERE identifier LIKE 'trust-device-%';`. The third because a trusted-device record lets a password skip the second factor for 30 days, and deleting sessions alone leaves it standing. **Run it as `app_runtime`** (the `DATABASE_URL` role): these tables are under FORCE ROW LEVEL SECURITY with policies for that role only, so as the table OWNER (FORCE applies to it too) every DELETE matches zero rows and still reports success, and a role with no grant gets `permission denied` — check the counts. The console shares `session`, so this covers it.
- **A member who cannot finish signing up** — their confirmation link expired (an hour) or never arrived. **Self-service since C30:** they sign in at `/login` with the password they chose; the screen says a new link is on its way, and it is mailed (at most three an hour per person — the ledger `auth_mail`). The link's page asks for that password again and confirms and signs in in one step. If they have forgotten the password, "Forgot your password?" on `/login` works for an unconfirmed account and confirms the address when it completes. **The operator's fallback**, for when neither works (mail not arriving at all — check the transport first): as `app_runtime`, with the address in LOWERCASE (Better Auth stores it that way, and the match is exact): `DELETE FROM "user" WHERE email = $1 AND NOT email_verified;` and **check that it says `DELETE 1`** — `DELETE 0` means there is no unconfirmed account at that address (it is confirmed, or it does not exist: see the next bullet). Then they sign up again. **What stops a statement here ever taking a workspace with it is the foreign key, not a query:** `member_user_id_fkey` is `ON DELETE RESTRICT`, so the DELETE fails with a key violation for anybody with a membership. *(An earlier version guarded it with `AND NOT EXISTS (SELECT 1 FROM member …)`, which does nothing here: `member` is under FORCE RLS, and as `app_runtime` with no tenant or user set it shows no rows at all, so the subquery is always empty. Never copy that pattern onto a table whose key CASCADEs.)*
- **An account somebody else signed up at a person's address** — a pre-account takeover. The report sounds like "a sign-up mail I did not ask for", "the confirmation page says that is not my password" or "an account I cannot sign in to with my own password". **Self-service since C30:** confirming an address takes the link AND the account's password, so neither the owner (no stranger's password) nor the stranger (no mailbox) can confirm it, and the stranger's password never starts working; the owner uses "Forgot your password?" — the confirmation page points there when their password is refused — which replaces the stranger's password, confirms the address and ends every session on the account. The name the stranger typed at sign-up stays on the account until the owner changes it at `/account` (possible once they belong to a workspace) — tell them to. **The operator's case:** the owner wants the account gone rather than recovered. As `app_runtime`, the address in lowercase: `DELETE FROM "user" WHERE email = $1;` — no `email_verified` filter — and read the answer: **`DELETE 1`**, the account is gone with its sessions, credential, factor and mail ledger, and the owner signs up again; **`DELETE 0`**, there is no account at that address; **a foreign-key error**, they already have a membership, so the account is in use — a founder decision, not an improvisation. *(A confirmed account whose second factor somebody else enrolled cannot arise from a pre-registration any more; for any other lost factor, `SECURITY.md` §3.5's two statements, after confirming the person's identity out of band.)*
- **A forgotten password — a member's.** Self-service since C30: "Forgot your password?" on `/login` → a link (at most three an hour per person; each works once, for an hour) → a new password. It ends every session and every sign-in in flight; the second factor, if any, is still asked for. A signed-in person changes theirs at `/account`.
- **A forgotten password — the OPERATOR's (the console).** The member plane's reset declines anybody with a `platformRole` — one credential row serves both planes, and the console's password must not be settable from a mailbox — and `scripts/create-test-member.ts` refuses such a user too, so the ONLY procedure is the operator's script, run by the operator, from a trusted machine, never by hand in SQL (**an agent never runs it against a real database**). From the repository root, with **production's** `DATABASE_URL` and `PLATFORM_DATABASE_URL` in the shell's environment (they win over `.env.local`):
  1. `pnpm exec tsx scripts/reset-ops-password.ts --email <operator address> --reason "<why>" --dry-run` — check that the `database:` line it prints names production and that the report names the right account;
  2. the same command without `--dry-run`.

  The new password is typed at the prompt, twice, without echo — from PowerShell or Windows Terminal, since Git Bash's mintty cannot hide input — or piped on stdin; a `--password` argument is refused, because it would land in shell history. Twelve to 128 characters. The script refuses anybody who is not a confirmed `SUPERADMIN`, and a refusal changes nothing. On success, in one transaction: the credential is replaced (created if there was none; the same password opens `/login`), **every session on both planes ends**, sign-ins waiting for a code and any reset links are cancelled, and `platform.password_changed` `{via: "operator"}` is written with SYSTEM as the actor, beside `withPlatform`'s `platform.system_job` row carrying the reason. The second factor and trusted devices are untouched, so the console asks for the same code as before. **If the report says the second factor is NOT ENROLLED, sign in at `/ops/login` at once and enrol** — until then the password alone opens the console (`SECURITY.md` §3.5, the bounded window). A lost authenticator is a different procedure (§3.5's two statements). A LEAKED ops password that is still known is changed at `/account` on the app, which ends every other session on both planes.
- Storage compromised: rotate R2 keys; presigned URLs are ≤ 15 min (PUT) / 60 s (GET).
