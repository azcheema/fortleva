**Decision 11 — time tracking reversed.**
- **What was decided before.** Decision 7 (2026-08-03) put time tracking on the skip list; `PLAN.md` (skip list) and `DATA_MODEL.md` §11 repeat it (line numbers of the v0.1 drafts omitted — both rows are now struck in place). The reasoning then was scope, not principle.
- **What changes.** Time is now first-class: Phase **2T** (after 2W Work, before 3 Portal) — per-task start/stop timer with a persistent pill, manual `1h 30m` entries, `RateCard` (kind `BILL`/`COST`, immutable rows, most-specific-wins resolved at entry *write* and snapshotted), `ProjectBudget` + once-per-threshold `BudgetAlert`, flat rollups (Σ task = epic = project = client, per member + total), `/projects/[key]/money`. Retention split: invoiced entries R1 (BFL 7 y, member pseudonymised on erasure); un-invoiced = HR class, tenant-configurable (default 2 y SE / 3 y US).

It becomes *övervakning* (DPIA-mandatory; MBL 11 § "viktigare förändring" for kollektivavtal-bound employers; NY/CT/DE notice statutes) only when the system captures activity the employee did not volunteer. Hence the **never-list** — idle detection, screenshots, app/URL/keystroke capture, presence broadcast, per-minute heatmaps, leaderboards, geolocation, peer-visible timelines — written into `PLAN.md`'s skip-list and `SECURITY.md` so no future session re-litigates it. - **Founder vocabulary, settled.** "Add cost per hour for that project so it can calculate the cost" = **the hourly rate charged to the client** = Fortleva `RateCard(kind BILL, scope PROJECT)`; hours × bill rate = the *value* of the work to the client. Fortleva additionally supports an **internal COST rate** (salary-derived, `RateCard(kind COST)`, `amountCiphertext` encrypted with AAD `tenantId:rate_card:<id>:amount`, `MEMBER → TENANT` resolution) for margin — an optional layer behind `finance.costRates.enabled`, CEO/finance-only (`rate:view_cost` ✦, `rate:manage_cost` ✦). **Decision 12 — vault as a product module; box stays pointer-only.**
- **What was decided before.** `PROJECT_BRIEF` §8, `DATA_MODEL.md` (`Project.hostingNotes`) and `CONTINUITY_BOX.md`: the product stores *pointers* to where credentials live, never live secrets. That remains true **for the continuity box** and is not reopened.
- **What changes.** The founder wants per-client/per-project credential storage next to the work; research converged on Hudu/IT Glue: credentials live *next to* the client/project/asset, typed, masked by default, reveal is an explicit audited act with step-up, expiring/view-once share links, and an asset registry with a unified expirations feed. Phase **3V** builds exactly that behind entitlement `vault`.
- **Crypto stance.** **Server-side envelope encryption, not E2EE.** `TenantKey(tenantId, keyId, wrappedDek, rootKeyId, status)` wrapped by the existing env root keyring (no KMS at v1 — a stated deviation from `SECURITY.md` §6's KMS seam, which stays as the seam); field-encryption **v2** format `v2.<rootKeyId>.<tenantKeyId>.<iv>.<ct>.<tag>` with AAD `tenantId:model:rowId:field` (§6 already specified AAD; the code lacked it); v1 ciphertext stays decryptable. **Lands in Phase 1b, before any encrypted app data exists — a one-way door.** E2EE was tried by Infisical/IT Glue and dropped or became a support burden; it would also break search, share links, server-generated TOTP and portal credential submission for 3–15 person agencies. The honest consequence: **the operator can technically decrypt** — `SECURITY.md` §6 says so, and the DPA/ROPA (Phase 7, C9/C14(b)) must say so in plain words. Mitigations are procedural and tested before UI: `CredentialItem` (class B, metadata) split from `CredentialSecret` (class A, ciphertext; a Contact can never SELECT it even for a CLIENT_VISIBLE item), Prisma `omit` on ciphertext, reveal budget (fail-closed), one field per reveal, `credential.revealed` audited in the same tx, secrets never in `search_index`/logs, offboarding flags credentials revealed in the last 90 d as "needs rotation".

Passcode-only links, TOTP-in-link, browser extension: not v1.
- **Relationship to the box.** `CONTINUITY_BOX.md` gains one paragraph: the box remains 2-of-3 Shamir, pointer-only (decision 1), and **auto-fills its "systems & assets" section from `ClientAsset` at seal time** and points at the vault; it never copies vault ciphertext.
- *(Amended 2026-10-02 — C52.)* The vault has two layers: the everyday vault, locked as a whole behind the step-up, and a **sealed layer** a client can open only by asking, with every owner emailed and a 7 + 2-day wait on silence. **Decision 15 — Fortleva is a PWA (2026-08-20): installable shell with 2T, Web Push in Phase 5, offline only in v1.5.**
- **What the founder asked.** "Will this app be a PWA?" — and, told that no document took a position (the specs had a responsive mobile layout, Web Push in Phase 5 and an offline timer queue in v1.5, none of them named "PWA"): "we need it to be PWA."
- **Decided.** (1) **Staged, so "PWA" never smuggles offline in.** *Stage A — installable shell, ships with Phase 2T* (the mobile timer pill is the first screen that earns a home-screen icon): a web-app manifest (`display: standalone`, `start_url: /home`, explicit `id`, regular + maskable icons, `theme_color`/`background_color` from the design tokens per theme, the Apple meta tags) and a **pass-through service worker** — registered from day 1 because Phase 5 push needs one and some browsers still gate the install prompt on one — that is **network-only for every navigation and every `/api/*` request**, precaches only immutable hashed `/_next/static/*` assets, and never writes a response that carried a session cookie into Cache Storage. *Stage B — Web Push (Phase 5, already planned)* rides on that worker; on iOS/iPadOS only an installed (home-screen) web app receives push, which is why A precedes B. *Stage C — offline (v1.5, unchanged)*: the offline timer queue (`TimeEntry.clientEventId`, reserved) and any cached tenant reads, **only after their own security pass** — a cached shell that shows one session's tenant data to a later or different session on a shared device is the worst-bug class, and visibility enforced at the data layer cannot be re-derived on the client (the reason local-first was rejected in ARC-18). (2) **Scope.** The manifest and worker belong to the **app host, member plane**, `scope: /`. The **portal** gets its own manifest at Phase 3 — `id: /portal`, `start_url: /portal`, `scope: /portal/`, installable, **no push** (client push stays on the skip list) — CP3 confirms the default. The **ops host gets neither**: the platform plane is MFA-mandatory admin, kept un-installable by design (no manifest, no worker, no install prompt — the ARC-11 phishing partition). Host and plane checks go through `src/config` (INV-D2), never a hardcoded hostname. (3) **Owned code.** A hand-written worker of a few dozen lines served from a route (ARC-24 already recorded `@serwist/turbopack` as preview); Serwist is re-evaluated only when Stage C needs real caching. (4) **Not a native app.** No Capacitor/TWA/store wrappers in v1; revisit only if Naxdor staff need background timers or notification behaviour the web platform does not grant installed web apps. (5) **Sign-out hygiene.** Sign-out and session revocation send `Clear-Site-Data: "cache", "storage"` where the browser honours it *(AMENDED 2026-10-08 by founder decision C74 (j): `"cache"` only — `"storage"` would unregister the worker and with it the device's push registration, so signing in again could never bring notifications back; a device's notifications stop because its session ended)*; the worker's precache is versioned by build id and old caches are deleted on activate.
- **Consequences recorded 2026-08-20.** `ARCHITECTURE.md` ARC-25 (the full pin); `PLAN.md` §0 item 4, §3 row 2T, Phase 2T screens, Phase 5 Web Push bullet, v2 backlog row, progress log; `UI.md` §3.3; `SECURITY.md` §3.6; `DATA_MODEL.md` §11 row; `AGENTS.md` one rule line. **No schema, no permission codes, no new sub-processor** (the push services were already listed for Phase 5).
